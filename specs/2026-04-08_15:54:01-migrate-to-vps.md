# Migrate from GCP Cloud Run to VPS Deployment

> Generated on: 2026-04-08
> Project: google-contacts
> Version: 1.0
> Status: Draft
> Type: Change Specification

## 1. Change Summary

This specification defines the migration of the Google Contacts MCP server from GCP Cloud Run to a VPS deployment. The migration adds HashiCorp Vault as a credential source, introduces Docker Compose for production deployment, updates DNS records to point to the VPS, and deprecates GCP-specific Terraform infrastructure. The core application logic (MCP server, OAuth 2.1 flow, People API wrapper) remains unchanged.

## 2. Current State Analysis

### 2.1 Project Overview

Google Contacts Manager is a Go 1.25 CLI application and MCP server that manages Google Contacts via People API v1. It uses Cobra for CLI, OAuth 2.1 for authentication (RFC 9728, RFC 8414, RFC 7591, PKCE S256), and is deployed on GCP Cloud Run. The project uses Terraform for infrastructure management with a two-layer approach: `init/` for foundational resources (state backend, service accounts, DNS zone) and `iac/` for application resources (Cloud Run, Artifact Registry, Secret Manager, domain mapping).

Key architecture:
- `internal/mcp/server.go`: MCP server with HTTP routing, auth middleware, tool registration
- `internal/mcp/oauth2.go`: OAuth 2.1 authorization server with `LoadCredentials()` that chains Secret Manager then local file
- `internal/mcp/auth.go`: Legacy auth handler (kept for backward compatibility)
- `internal/cli/cli.go`: Cobra CLI with `mcp` subcommand accepting `--secret-name`, `--secret-project`, `--credential-file`, `--base-url`, `--host`, `--port`
- `internal/contacts/service.go`: People API wrapper
- `pkg/auth/auth.go`: Dual-mode auth (context + file), context keys for OAuth config and tokens

The `Config` struct in `server.go` holds: `Host`, `Port`, `BaseURL`, `SecretName`, `SecretProject`, `CredentialFile`.

### 2.3 Relevant Architecture

**Credential loading** (`oauth2.go:LoadCredentials`):
1. Secret Manager (if `secretProject` and `secretName` are set): calls `loadFromSecretManager()` which creates a `secretmanager.NewClient()` and reads `projects/{project}/secrets/{name}/versions/latest`
2. Local file (if `credentialFile` is set): reads from filesystem
3. Falls through to error if neither source provides credentials

**Config flow**:
- CLI flags (`cli.go` line 1241-1246) set variables `mcpPort`, `mcpHost`, `mcpBaseURL`, `mcpSecretName`, `mcpSecretProject`, `mcpCredentialFile`
- `runMCP()` (line 818) reads env var fallbacks for `HOST`, `PORT`, `SECRET_PROJECT`/`PROJECT_ID`, `SECRET_NAME`, `BASE_URL`
- Constructs `mcpserver.Config` and passes to `NewServer().Run()`
- `Run()` initializes `OAuth2Server` with `OAuth2ServerConfig{BaseURL, SecretProject, SecretName, CredentialFile}`

**Terraform structure** (`iac/`):
- `local.tf`: Loads `config.yaml`, extracts GCP project, region, Cloud Run config, custom domain
- `workload-mcp.tf`: Artifact Registry, Cloud Run service, IAM permissions, env vars (HOST, SECRET_NAME, BASE_URL, PROJECT_ID)
- `docker.tf`: Docker provider, builds image locally, pushes to Artifact Registry
- `dns-domain.tf`: Cloud Run domain mapping, CNAME record to `ghs.googlehosted.com`
- `secrets.tf`: Secret Manager secret for OAuth credentials
- `provider.tf`: Backend config (auto-generated from init)

**Dockerfile**: Multi-stage (golang:1.25 builder -> alpine), non-root `appuser`, HEALTHCHECK on `/health`, `ENTRYPOINT ["/app/google-contacts", "mcp"]`

**Domain**: `contacts.mcp.scm-platform.org` via Cloud Run domain mapping with CNAME to `ghs.googlehosted.com`

## 3. Requested Modifications

### MOD-001: HashiCorp Vault Credential Loading

- **Type:** Add
- **Description:** Add a new credential source that loads Google OAuth credentials from HashiCorp Vault KV v2 secret store, accessible via HTTP API.
- **Rationale:** The VPS environment uses Vault for centralized secret management instead of GCP Secret Manager. The same Vault path will be shared across all MCP servers deployed on the VPS.
- **Priority:** Must-have
- **Details:**
  - New method `loadFromVault()` on `OAuth2Server` struct
  - Vault KV v2 API: `GET {VAULT_ADDR}/v1/secret/data/{VAULT_SECRET_PATH}`
  - Default secret path: `secret/credentials/google-credentials`
  - HTTP request with `X-Vault-Token` header
  - Response JSON: `{ "data": { "data": { ... credentials JSON ... } } }` (KV v2 nesting)
  - The credentials payload is the same JSON format as the local file (Google OAuth client credentials)
  - New fields on `OAuth2ServerConfig`: `VaultAddr`, `VaultToken`, `VaultSecretPath`
  - Env vars: `VAULT_ADDR` (default `http://vault:8200`), `VAULT_TOKEN`, `VAULT_SECRET_PATH`
  - No external Go dependency required: uses `net/http` + `encoding/json` (already imported)

### MOD-002: Docker Compose Production Deployment

- **Type:** Add
- **Description:** Create Docker Compose configuration for running the MCP server on VPS with proper networking and environment configuration.
- **Rationale:** VPS deployment uses Docker Compose instead of Cloud Run. The external `proxy-network` connects to the VPS reverse proxy (nginx) for TLS termination and routing.
- **Priority:** Must-have
- **Details:**
  - `docker-compose.prod.yml`: Single service (`google-contacts-mcp`), builds from Dockerfile, exposes port 8080, uses external `proxy-network`, loads env from `/app/data/google-contacts/.env`
  - `environments/prod/.env.example`: Template with all env vars (no secret values), committed to git
  - Variables: `HOST`, `PORT`, `BASE_URL`, `VAULT_ADDR`, `VAULT_TOKEN`, `VAULT_SECRET_PATH`, `SECRET_NAME`, `SECRET_PROJECT`, `CREDENTIAL_FILE`

### MOD-003: VPS Deployment Makefile Target

- **Type:** Add
- **Description:** Add a `deploy-vps` target to the Makefile that deploys the application to the VPS via SSH.
- **Rationale:** Provides a single-command deployment workflow consistent with the existing `make deploy` for Cloud Run.
- **Priority:** Must-have
- **Details:**
  - SSH to VPS, undeploy existing container, run `vps-deploy.sh` script
  - The `vps-deploy.sh` script is expected to exist on the VPS (part of VPS base infrastructure)
  - VPS deploy script handles: git clone/pull, Docker build, container start, nginx route configuration, Let's Encrypt certificate auto-provisioning
  - VPS host: `31.97.54.67`
  - VPS app data directory: `/app/data/google-contacts/`
  - VPS app source directory: `/app/src/google-contacts/`

### MOD-004: DNS Record Change

- **Type:** Change
- **Description:** Change the DNS record for the MCP server domain from a CNAME pointing to `ghs.googlehosted.com` to an A record pointing to the VPS IP address.
- **Rationale:** Cloud Run domain mapping uses CNAME to Google's hosting. VPS requires a direct A record to the server IP.
- **Priority:** Must-have
- **Details:**
  - **Current:** CNAME `contacts.mcp.scm-platform.org` -> `ghs.googlehosted.com.`
  - **New:** A record `google-contacts.scm-platform.org` -> `31.97.54.67`
  - Domain name changes from `contacts.mcp.scm-platform.org` to `google-contacts.scm-platform.org` (simpler naming convention)
  - TTL: 3600 seconds
  - DNS provider: Google Cloud DNS (managed via `gcloud` CLI, not Terraform)
  - Command: `gcloud dns record-sets create "google-contacts.scm-platform.org." --zone=scm-platform-org --type=A --ttl=3600 --rrdatas="31.97.54.67"`
  - The old CNAME record must be deleted: `gcloud dns record-sets delete "contacts.mcp.scm-platform.org." --zone=scm-platform-org --type=CNAME`
  - TLS certificate will be provisioned by Let's Encrypt via the VPS nginx/certbot stack (not Google-managed)
  - **GCP Console update required:** Authorized redirect URI must be changed from `https://contacts.mcp.scm-platform.org/oauth/callback` to `https://google-contacts.scm-platform.org/oauth/callback`

### MOD-005: Credential Loading Priority Chain

- **Type:** Change
- **Description:** Modify the credential loading order in `LoadCredentials()` to insert Vault between Secret Manager and local file.
- **Rationale:** On VPS, Vault is the primary credential source. Secret Manager is kept for backward compatibility during migration. Local file remains as ultimate fallback.
- **Priority:** Must-have
- **Details:**
  - **Current priority:** 1) Secret Manager, 2) Local file
  - **New priority:** 1) Secret Manager, 2) Vault, 3) Local file
  - Each source logs success/failure at load time
  - If a source fails, execution falls through to the next source silently (with log warning)
  - If all sources fail, return error with message listing all attempted sources
  - The same pattern must be applied in both `oauth2.go:LoadCredentials` (OAuth2Server) and `auth.go:loadOAuthCredentials` (AuthHandler, legacy)

### MOD-006: Deprecate GCP Cloud Run Terraform Infrastructure

- **Type:** Remove
- **Description:** Deprecate the Terraform files that manage GCP Cloud Run deployment. Files will be renamed with `.deprecated` suffix rather than deleted, following the existing pattern (`database-firestore.tf.deprecated`).
- **Rationale:** The VPS deployment replaces Cloud Run. Keeping the files with a `.deprecated` suffix preserves the infrastructure-as-code history for reference without Terraform attempting to manage those resources.
- **Priority:** Should-have
- **Details:**
  - Rename `iac/workload-mcp.tf` to `iac/workload-mcp.tf.deprecated`
  - Rename `iac/docker.tf` to `iac/docker.tf.deprecated`
  - Rename `iac/secrets.tf` to `iac/secrets.tf.deprecated`
  - Rename `iac/dns-domain.tf` to `iac/dns-domain.tf.deprecated`
  - Keep `iac/local.tf` and `iac/provider.tf` (still needed if DNS zone management stays in Terraform)
  - Keep `init/` entirely (DNS zone, state backend, service accounts remain useful)
  - Before renaming, run `terraform state rm` for each managed resource to avoid Terraform trying to destroy them
  - Alternatively, run `make undeploy` to cleanly destroy Cloud Run resources before deprecating the files

### 4.5 Dependencies & Risks

**New dependencies:**
- None (Vault HTTP API accessed via stdlib `net/http` + `encoding/json`)

**Dependencies that can be removed (future):**
- `cloud.google.com/go/secretmanager` could be removed if Secret Manager support is fully dropped. However, it must be kept for backward compatibility during migration.

**Breaking changes:**
- Domain name changes from `contacts.mcp.scm-platform.org` to `google-contacts.scm-platform.org`. Any MCP client configurations pointing to the old domain must be updated.
- GCP OAuth Console authorized redirect URI must be updated to the new domain before the DNS switch.

**Migration risks:**
- **DNS propagation delay:** After switching the DNS record, there will be a propagation window (typically minutes, up to 48 hours) where some clients resolve to the old Cloud Run service and others to the VPS. During this period, OAuth callbacks may fail if the redirect URI has already been updated in GCP Console.
- **TLS certificate provisioning:** Let's Encrypt certificate provisioning on VPS requires the DNS to already point to the VPS IP. There will be a brief window (seconds to minutes) where HTTPS is not available on the new domain.
- **Vault availability:** If Vault is unavailable and Secret Manager is not configured, the server will fail to start. This is the expected fail-fast behavior.

**Rollback strategy:**
1. Revert DNS A record back to CNAME pointing to `ghs.googlehosted.com`
2. Restore OAuth callback URI in GCP Console to old domain
3. Cloud Run service remains functional (not destroyed until MOD-006 is completed)
4. MOD-006 (Terraform deprecation) must be the last step executed, after VPS is confirmed working

## 5. New & Modified Requirements

### New Requirements

#### FR-NEW-001: Load Credentials from HashiCorp Vault

- **Description:** The system must be able to load Google OAuth credentials from a HashiCorp Vault KV v2 secret store via HTTP API.
- **Inputs:**
  - `VAULT_ADDR`: Vault server address (e.g., `http://vault:8200`)
  - `VAULT_TOKEN`: Authentication token for Vault API
  - `VAULT_SECRET_PATH`: Path to the secret in Vault KV v2 (e.g., `secret/credentials/google-credentials`)
- **Outputs:** Parsed Google OAuth credentials (client ID, client secret) loaded into the OAuth config
- **Business Rules:**
  - The Vault KV v2 API response has double-nested `data`: `{ "data": { "data": { <credentials> } } }`
  - The inner `data` object must contain the same JSON structure as a Google OAuth credentials file
  - HTTP GET with `X-Vault-Token` header must be used for authentication
  - If `VAULT_ADDR` or `VAULT_TOKEN` are empty, Vault loading must be skipped silently (with log message)
  - If Vault returns a non-200 status or the response cannot be parsed, the system must log the error and fall through to the next credential source
  - HTTP timeout for Vault requests must be 5 seconds
- **Priority:** Must-have

#### FR-NEW-002: Docker Compose Production Configuration

- **Description:** The system must provide a Docker Compose configuration for production VPS deployment.
- **Inputs:** Environment variables from `/app/data/google-contacts/.env`
- **Outputs:** Running container on port 8080, connected to `proxy-network`
- **Business Rules:**
  - The compose file must use `docker-compose.prod.yml` as filename
  - The service must connect to the external Docker network `proxy-network`
  - Environment file path on VPS: `/app/data/google-contacts/.env`
  - Container must restart unless explicitly stopped (`restart: unless-stopped`)
  - Container name must be `google-contacts-mcp`
  - Build context must be the project root with `Dockerfile`
- **Priority:** Must-have

#### FR-NEW-003: VPS Deployment Target

- **Description:** The Makefile must include a `deploy-vps` target that deploys the application to the VPS via SSH.
- **Inputs:** VPS IP (`31.97.54.67`), SSH access, `vps-deploy.sh` script on VPS
- **Outputs:** Running application on VPS accessible via the configured domain
- **Business Rules:**
  - The target must SSH to the VPS and execute the deployment script
  - The deployment script (`vps-deploy.sh`) is part of VPS base infrastructure and must not be created by this project
  - The target must pass the project name and git repository URL to the deploy script
  - The target must print the resulting URL after deployment
- **Priority:** Must-have

#### FR-NEW-004: Environment Variable Template

- **Description:** The system must provide a `.env.example` file documenting all required and optional environment variables for VPS deployment.
- **Inputs:** N/A (template file)
- **Outputs:** `environments/prod/.env.example` committed to git
- **Business Rules:**
  - Must contain all env vars: `HOST`, `PORT`, `BASE_URL`, `VAULT_ADDR`, `VAULT_TOKEN`, `VAULT_SECRET_PATH`, `SECRET_NAME`, `SECRET_PROJECT`, `CREDENTIAL_FILE`
  - Must contain comments explaining each variable
  - Must not contain actual secret values
  - Must indicate which variables are required vs optional
- **Priority:** Must-have

### Modified Requirements

#### FR-MOD-001: Credential Loading Chain (references oauth2.go LoadCredentials)

- **Original behavior:** LoadCredentials tries: 1) Secret Manager (if configured), 2) Local file (if configured), 3) Error
- **New behavior:** LoadCredentials tries: 1) Secret Manager (if configured), 2) Vault (if configured), 3) Local file (if configured), 4) Error
- **Reason for change:** VPS deployment uses Vault instead of Secret Manager for credential storage
- **Business Rules:**
  - Each source must log its success or failure
  - Each source failure must be non-fatal (fall through to next)
  - Final error message must list all sources that were attempted
  - The same chain must be implemented in both `OAuth2Server.LoadCredentials()` and `AuthHandler.loadOAuthCredentials()`

#### FR-MOD-002: Server Config Struct (references server.go Config)

- **Original behavior:** Config contains: `Host`, `Port`, `BaseURL`, `SecretName`, `SecretProject`, `CredentialFile`
- **New behavior:** Config adds: `VaultAddr`, `VaultToken`, `VaultSecretPath`
- **Reason for change:** New fields needed to pass Vault configuration from CLI to OAuth2Server
- **Business Rules:**
  - New fields must be string type
  - New fields must be optional (empty string means "not configured")

#### FR-MOD-003: MCP CLI Flags (references cli.go mcp command)

- **Original behavior:** MCP command accepts: `--port`, `--host`, `--base-url`, `--secret-name`, `--secret-project`, `--credential-file`
- **New behavior:** MCP command additionally accepts: `--vault-addr`, `--vault-token`, `--vault-secret-path`
- **Reason for change:** Vault configuration must be settable via CLI flags with env var fallbacks
- **Business Rules:**
  - `--vault-addr` falls back to `VAULT_ADDR` env var
  - `--vault-token` falls back to `VAULT_TOKEN` env var
  - `--vault-secret-path` falls back to `VAULT_SECRET_PATH` env var
  - All three flags default to empty string (not configured)
  - Existing flags must remain unchanged for backward compatibility

#### FR-MOD-004: DNS Domain (references custom-domain-mapping spec SC-001)

- **Original behavior:** `contacts.mcp.scm-platform.org` CNAME to `ghs.googlehosted.com`
- **New behavior:** `google-contacts.scm-platform.org` A record to `31.97.54.67`
- **Reason for change:** VPS does not use Google's domain mapping infrastructure
- **Business Rules:**
  - Old CNAME record must be deleted before or after creating the new A record
  - DNS changes must be performed via `gcloud dns` CLI commands (not Terraform)
  - TTL for new A record: 3600 seconds
  - OAuth redirect URI in GCP Console must be updated to new domain

## 9. Consistency Notes

### Inconsistency with Custom Domain Mapping Spec

The existing spec `specs/2026-02-22_13:43:06-custom-domain-mapping.md` defines the Cloud Run domain mapping for `contacts.mcp.scm-platform.org` with CNAME to `ghs.googlehosted.com`. This migration spec supersedes that infrastructure setup:

- **SC-001 (Deploy Custom Domain):** The Terraform-based Cloud Run domain mapping workflow is replaced by manual `gcloud dns` commands and VPS nginx configuration. The concept of a custom domain remains, but the implementation is entirely different.
- **SC-002 (Change project_id):** No longer relevant for the application deployment, though the DNS zone may still live in a GCP project.
- **Resolution:** The custom domain mapping spec remains as historical documentation. This migration spec takes precedence for all deployment-related requirements. The existing spec must NOT be modified.

### Credential Loading Duplication

Both `oauth2.go` (OAuth2Server) and `auth.go` (AuthHandler) implement credential loading with similar logic. This migration adds Vault support to both. The duplication is acknowledged and must be maintained consistently. A future refactoring to extract a shared `CredentialLoader` could be tracked in the backlog.

### Domain Name Change

The domain changes from `contacts.mcp.scm-platform.org` (hierarchical MCP namespace) to `google-contacts.scm-platform.org` (flat project-name namespace). This is a breaking change for any existing MCP client configurations. All Claude MCP server configurations must be updated to the new domain.

### Rollback Plan

If VPS deployment fails after DNS switch:
1. Re-create CNAME record: `gcloud dns record-sets create "contacts.mcp.scm-platform.org." --zone=scm-platform-org --type=CNAME --ttl=300 --rrdatas="ghs.googlehosted.com."`
2. Delete A record: `gcloud dns record-sets delete "google-contacts.scm-platform.org." --zone=scm-platform-org --type=A`
3. Revert OAuth redirect URI in GCP Console
4. Cloud Run service is still running (Phase 4 not yet executed)

### Feature Flag Consideration

No feature flag is needed. The credential loading chain is additive: Vault is simply inserted as an additional source. If Vault is not configured (empty env vars), it is skipped. The existing Secret Manager + local file flow continues to work unchanged.
